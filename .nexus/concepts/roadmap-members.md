# Roadmap Members

A resolved roadmap holds one ordered list of members, and a member is either an epic that has been planned or an epic nobody has planned yet. A planned member contributes its stories, their bodies and the edges between them; an unplanned member carries only its own title and body. Every member states which kind it is, so a reader can see where planned work runs out without going back to the issue graph.

## How It Works

An unplanned member's body is carried because it is the only material that member has, and no later phase may return to the issue graph to learn what a member says. A planned member's body is not carried, because nothing downstream reads it and fetching it would cost a call per member.

Kind is stated, not inferred: an epic whose stories were all withdrawn also resolves with no stories, so an empty story list answers nothing.

Members are ordered by ascending issue number, with one exception: a member that planned work waits on is pulled ahead of the work waiting on it. Only edges with an unplanned member at one end are read, taken from blockers already fetched for the stories. Two planned members already have their relationship expressed story by story, and a coarse edge between them would flatten it. Every such edge runs from an unplanned member to a planned one, so no chain and no cycle can form.

## Key Invariants

1. Every member states its kind, and no reader has to return to the issue graph to learn it.
2. An unplanned member carries the title and the body of its issue and no stories, and the roadmap holds no story attributed to it.
3. A planned member's stories, their bodies and their edges are what they were before a second kind of member existed, and the story order over them is unchanged.
4. Re-resolving an unchanged issue graph gives the same members in the same order, and ascending issue number is the order's only tie-break.
5. A member that planned work waits on sits before that work in the order.
6. The member order says where planned work runs out. It is not a teaching order, and nothing derives a teaching sequence from it.
7. The list is derived and never committed; nothing depends on the shape of one an earlier run wrote.

## Integration Points

- [roadmap-resolution](roadmap-resolution.md) — names the issues this list is built from, reads each one, and decides which kind of member it becomes.
- [story-concept-extraction](story-concept-extraction.md) — reads the stories planned members contribute; a member nobody has planned yet gives it nothing to read.

## Decision Log

### 2026-09-20 — #64 — A roadmap holds two kinds of member, in one order

A roadmap a learner is taught from is still growing, so the unplanned tail of an initiative is exactly the part nobody has written yet. The old shape was a bare ascending list of epic numbers with stories hanging off it, and it could hold planned epics only. It was replaced rather than kept beside a new list, because two lists holding the same members can disagree and a reader can pick the wrong one, and because the list is derived and regenerated by re-resolving, so replacing its shape cost no migration. Kind is stated on every member because an epic whose stories were all withdrawn also resolves with no stories, so inference would call that epic unplanned. The rule that this list is never committed is now held by the repository's ignore rules rather than by review, because the list now carries an unplanned member's whole issue body, which reads like material worth keeping. An unplanned member is never called a stub in this list or in any message about it, because that word already names a slice stub in the plan draft and one word for two things makes a refusal unreadable. Refuted alternative: give unplanned members synthetic stories, so one story order covers everything and nothing needs a second concept. It lost on downstream safety, because every later phase iterates stories and a story with no acceptance criteria would flow into extraction, the draft, the rewrite and the committed plan. Refuted alternative: order members on the full member-level graph instead of on the edges that touch an unplanned member. It lost because it would flatten the finer story order between two planned members and would add a member-level cycle refusal for cycles the restricted rule makes impossible.
